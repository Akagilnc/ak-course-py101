# Py101 Course Style

这份文件记录 Python 101 课程改版的长期风格标准。后续改课件时，先读这里，再动 Markdown。

## 课程对象

- 学员是夜校非代码专业同学，默认已经上了一天班，注意力和精力都有限。
- 课程目标不是训练程序员，而是让学员能看懂简单脚本、手改少量代码、理解基础数据分析概念，并知道如何用 AI 辅助学习。
- 课堂要有实际收获感。少动手不等于内容变水，听的部分也要有信息密度。
- 很多学员只是下班后来打发时间，后续继续写 Python 的概率不高。课程优先让大家觉得有意思、听懂一些生活里的数据问题、获得一点正反馈，而不是强调训练强度。

## 内容底稿

- Markdown 是内容源，HTML 是展示层，Keynote 是旧资料参考。
- 内容结构没定前，不生成或大改 HTML。
- 从旧 Keynote 搬来的有效内容，优先同步到 Markdown。
- 课件内容和讲义内容不是一回事。Markdown 可以记录讲解逻辑，HTML 只放适合投屏的内容。

## 文字风格

- 写给课堂用，不写成 agent 工作报告。
- 少铺垫，少总结式废话，少重复提醒。
- 用户删掉的内容不要补回来。删除本身是风格反馈。
- 避免“不要 xxx”式提醒，除非它能阻止真实错误；很多时候不说，学生反而不会想到岔路。
- 问题页聚焦业务问题；答案页给关键结论；技术解释服务当前代码，不独立炫技。

## 示例标准

- 示例必须有现实理由，优先用股票、生活价格、课堂实际文件，不用抽象玩具值。
- 新概念要反复出现在真实例子里。`for`、`while`、list、下标、文件读取、字典这种概念不能一页讲完就走。
- 讲 list / 下标时，用真实字段，例如 `["贵州茅台", "1709", "1705"]` 和 `parts[0]`、`parts[1]`、`parts[2]`。
- 避免 `[-1, 1, 3]`、`[1, 4, 2]` 这种没有记忆点的魔幻数字例子。
- 说“读文件”就写真实读文件代码，例如 `file = open(...)`、`lines = file.readlines()`、`file.close()`。
- 文件读取是老大难概念。后续例子如果继续用同一份数据，也要重复写 `open/readlines/close`，不要为了省字写“沿用上面的 lines”。
- 单日股票例子使用“开盘价格 / 收盘价格”。只有明确比较两天时，才使用“昨日 / 今日”。
- 输出要实际跑过。讲义里的标准输出必须和代码一致。
- 涨跌幅给学生看时，优先输出成带 `%` 的形式。
- 字符串输出优先沿用旧课风格的 `.format()`，例如 `"{} {}%".format(name, percent)`。
- 业务含义明确的数字不要裸写成魔法数字。比如“每股涨 1 元”要定义成 `price_change = 1`，否则初学者会卡在这个数字从哪里来。

## 数据分析标准

- 数据分析知识点要跟着每个例子出现，不只在最后集中堆一页。
- 同一批数据可以回答多个问题：逐条计算、找最大/最小、统计数量、观察行业分布。
- 指标选择要讲清楚。比如“跌的钱最多”和“跌幅最大”可能不是同一只股票。
- 行业视角可以自然引入：白酒、银行、新能源、地产、科技、资源、通信等类别可能表现不同。
- 结论和投资建议要区分。课堂数据分析只能说明这批数据里的现象。
- L1 实际上课反馈：后半如果只是代码页、问题页、答案页，很快讲完，课堂密度不够。更有效的填充不是加更多 AI 讲解，而是让学生低压力参与：先猜输出、手写一段短代码、手算一组数据、改一个参数、再看结果。
- L1 后半每个数据例子最好有一个可现场操作的“停顿点”。例子 3 让学生手写并看结果，现场证明比单纯讲答案更能撑住时间。
- L1 实际上课反馈：问题不能一页全摊开，否则会剧透答案、压缩课堂互动。后半问题页要分层揭示：先问直觉题，再补条件，再给答案和现实含义。
- L1 后半需要和前半 `if` 呼应，例子梯度应该是：例子 1 完全顺序执行、例子 2 出现简单 `if`、例子 3 更真实也稍微复杂一些。避免三个后半例子都只是顺序计算。
- 后半数据例子要明确抓住“让人惊讶的点”。例如“都涨 1 元，收益能差很多”“跌 50% 后要涨 100% 才回本”，比泛泛解释公式更能撑住课堂。

## Quiz 和复习节奏

- L3、L5、L7 这类隔了一周再来的课，课前 quiz 不能只复习上一节内容，也要补 L1 基础：变量、赋值、函数、参数、返回值、`print()`、`if`、简单涨跌幅。
- 隔周课的 quiz 可以稍微多一些，用来把基础概念叫醒；但展示结构仍然要稳定，参考 L2：每页完整代码块 + 两道题，不要每节课换一种 quiz 形态。

## AI 演示标准

- AI 演示要让 AI 做有用的事：读原始数据、算结果、检查结果、翻译报错、写普通人能看懂的总结。
- 不要让 AI 主要讲技术细节。技术细节由老师讲，AI 更适合做“帮普通人理解”和“辅助检查”的角色。
- 好的 AI 演示可以有戏剧性：AI 算对了就是提效，AI 算错了就用程序输出做标准答案。
- 拍照给 AI 的页面要自包含。不能要求现场翻回前面几页找代码或数据。
- L1 实际上课反馈：AI 段不能单独承担 10-15 分钟的课堂容量。AI 更适合作为 5 分钟左右的插入点，用来解释一段结果、生成类比、检查计算或翻译报错。

## 投影和代码页

- 教室投影按 1080p 设计，并且顶部可能被裁掉，页面上方要留安全距离。
- 课堂阅读代码建议 18-20 号以上。
- 给 AI 拍照的代码页可以稍小，但必须同屏完整，没有滚动条。
- 单页代码尽量一屏讲完。超过一屏，优先拆页或换成老师 IDE 手写。
- 问题页一页 2-3 个短问题，答案页只放关键输出和一句结论。
- 如果问题之间存在提示关系，宁可拆成多页，也不要放在同一页互相剧透。

## 已踩坑

- 不能说“模拟读文件”，然后又把 13 行数据写成 Python 字符串或手造 list。这会破坏课堂概念一致性。
- 不能把后半数据分析只做一个例子。2.5 小时课程需要足够的听讲密度和可控节奏。
- 不能把 AI 演示写成“解释 for / list / 下标”。这对不会编程的人吸引力弱。
- 不能只在一个例子里提 list / 下标，后面就默认学员懂了。难概念要在后续例子里继续重复。
